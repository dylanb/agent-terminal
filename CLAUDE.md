# CLAUDE.md

Agent Terminal — Electron app that hosts coding agents (Claude Code, Codex, …) in a PTY-attached shell session, renders it with xterm.js, tees output into a main-process `@xterm/headless` shadow screen model, and provides a monitor pane that captures output and injects input back into the agent.

`terminal-web-ui-spec.md` (v2.94) is the authoritative spec. Every subsystem implements a numbered section of it; when code and spec disagree, the spec wins — or the spec gets a changelog entry. Cite spec sections (e.g. §9.3) in code review discussion rather than re-arguing settled design decisions.

## Commands

This repo uses **pnpm** (see `packageManager` in `package.json`). `.npmrc` pins `node-linker=hoisted` so `@electron/rebuild` and electron-builder see a flat `node_modules`; `pnpm.onlyBuiltDependencies` allows node-pty/electron/esbuild to run their install scripts (pnpm v10 blocks build scripts by default).

```
pnpm install        # runs the postinstall electron-rebuild for node-pty automatically
pnpm run rebuild    # electron-rebuild -f -w node-pty — REQUIRED after install or Electron bump
pnpm run dev        # electron-vite dev (renderer HMR)
pnpm run build      # type-check + electron-vite build
pnpm test           # vitest: tests/unit + tests/integration
./scripts/e2e-podman.sh        # playwright _electron e2e in Podman/Xvfb — the canonical local e2e run (real PTY/display)
./scripts/e2e-podman.sh "<-g>" # filter to matching tests
pnpm run test:e2e   # raw playwright e2e — needs a focusable display; on macOS a bare subprocess launch can't focus, so prefer the Podman harness above
```

**Always run the e2e locally via the Podman harness (`docs/e2e-podman.md`) before claiming a change done — do not defer e2e to CI.**

`node-pty` is a native module compiled against Electron's ABI. If main-process startup fails with a NODE_MODULE_VERSION error, run `pnpm run rebuild`.

## Requesting / awaiting a Copilot PR review

Use `scripts/await-copilot-review.sh <pr> [--request] [--check]` (portable bash; macOS + Linux, no `jq`) — never hand-roll a poll. Two non-obvious traps it removes: the Copilot reviewer's login is `copilot-pull-request-reviewer[bot]` on `/pulls/{n}/reviews` but `Copilot` on `/pulls/{n}/comments`, so a single exact-login filter silently matches zero; and a wrong poll predicate is indistinguishable from "review not posted yet", so the script baselines the matched count and (`--check`) validates the predicate against the reviews already on the PR before waiting. If you must filter reviews yourself, match `user.type=="Bot"` + a case-insensitive `copilot`, not an exact login.

## Architecture (orientation only — details in the spec)

- `src/main/` — PTY lifecycle (§5), shadow terminal + quiescence (§8), injection API (§9.3), IPC handlers. node-pty and the shadow live here, never in the renderer. The flow **audit recorder** (§25) also lives here (`auditRecorder.ts` + `auditPaths.ts`): observe-only, best-effort, it writes each run's append-only YAML under `~/.agent-terminal/audit/` and never throws into the flow path.
- `src/preload/` — contextBridge exposing the `term` and `monitor` namespaces (§6). No raw `ipcRenderer` in the renderer.
- `src/renderer/` — terminal pane (xterm + app-owned selection, §7) and monitor pane (§9).
- `src/shared/ipc.ts` — the typed IPC contract. This file is the single source of truth for channel names and payload shapes; main, preload, and renderer all import from it.
- **Semantics shared by main and renderer get one definition in `src/shared/`, imported by both — never re-implemented per side.** This generalizes the `ipc.ts` rule from the wire shape to the *meaning* on top of it: any classification or identity that both processes must agree on — what counts as "the same occurrence" for dedup, which statuses mean "blocked on a human", and the like — lives in a shared module so the two sides cannot drift. Two parallel copies that "obviously agree today" are the bug; a behavior-preserving change to one side must be unable to desync them. The current examples are `src/shared/occurrence.ts` (dedup identity), `src/shared/loopStatus.ts` (human-needed classification), `src/shared/audit.ts` (the §25 audit vocabulary, event classifiers, serialize↔parse pair, and timeline reconstructor — one definition for the main-process writer, the tests, and a future viewer), and `src/shared/shellQuote.ts` (POSIX shell quoting — one primitive for the main-process shim/PATH generation and the renderer's drop-to-paste path).

## Test-driven development

- **TDD is mandatory for every code change — RED first, no exceptions.** No code gets written without a failing test being written and run first. Write the failing test, run it and observe the failure (the assertion message, not just an exit code), then make it pass with the smallest change that does so, then refactor. This applies to bug fixes (start with a regression test that reproduces the bug), new features (start with a test for the acceptance criterion), refactors of behavior-bearing code (start with a pinning test against the current behavior), and API changes (start by updating the test to the new contract and watching it fail to compile or fail at runtime). Tightening an existing test until it would catch the bug counts as a new test.
  - **Glue and wiring are code.** Button handlers, event subscriptions, IPC wiring, lifecycle hooks — all of it. A passing test for a lower-level helper does **not** license writing the layer above it untested: the failing test must observe the *change's own* behavior at its own observable boundary. If the change wires a button, the RED test clicks the button (e2e or DOM-level); if it subscribes to an event, the RED test fires the event and observes the consequence. "A test exists nearby" is the loophole that produced this rule.
  - **The sole exemption is code that cannot be covered at all.** Claiming it requires, *before any code is written*: (1) an explicit written statement of exactly what cannot be tested and why no layer of the stack (unit, integration, Playwright e2e) can observe it, and (2) a recorded gap — an unchecked §12-style checklist item or `// TODO(owner):` — so the hole is visible, never discovered later. "Untestable" is a design smell, not a license, and "hard/slow to test" (process-table checks, alt-buffer gestures, timing) does not qualify — those get the slow test.
  - Edits with nothing observable to test — comment/doc-only changes, formatting — are outside the rule's scope, but anything that can alter behavior (including renames, config, build files, dependency bumps) is in: if existing tests can't fail when the edit is wrong, write one that can, or invoke the exemption above in writing.
  - Tests written after the implementation are pinning tests, not TDD — they never satisfy this rule for new code. Calling tests "manual verification" or "I'll add tests after" is never acceptable.
- **Evidence of a clean, complete test run is required before declaring any change clean, done, or ready for review — no exceptions.** "Clean/done/ready" is a claim about observed reality, not about the diff: you MUST have run the *full* relevant suite (unit, integration, and the Playwright e2e — the e2e green bar needs a focusable display, so **always run it locally in the Podman/Xvfb harness** (`./scripts/e2e-podman.sh`, `docs/e2e-podman.md`) and **never defer e2e evidence to CI**; a macOS subprocess launch cannot give focus/clipboard and its red bar is not evidence of anything) and seen it pass. Show the evidence — the passing tally — when you make the claim. A suite that has never been observed green in a valid environment is **worse than no suite**: its redness gets pre-explained as "the environment" and stops being a signal, which is exactly how a real defect (e.g. a synchronous throw that aborted window creation and turned the entire e2e bar red) hides in plain sight. **A failing or unrunnable test — or broken test infrastructure — is never a thing to normalize, defer, or explain away.** The e2e is runnable locally via the Podman harness, so "I'll let CI run it" is not an acceptable substitute for running it yourself; **only** when the Podman harness itself cannot run (Podman absent, machine unprovisionable) is it grounds to declare an impasse and ask the operator for help. Either get to a clean complete run locally, or stop and escalate; never report "clean" over a red or un-run bar, and never push and rely on CI in place of a local Podman e2e run.
- **Tests MUST exercise observable behavior, NOT implementation.** **Treating this as optional is a blocker-level violation.** A test asserts what a caller of the unit-under-test can observe from the outside: return values, thrown errors, bytes written to the PTY, IPC payloads emitted on a contract channel (§6), text read back out of the shadow buffer through its public read path, DOM state the user can see. A test MUST NOT assert: which private method was called, in what order, how many times; the internal data structure shape; the exact escape-sequence parsing steps; the names of intermediate variables; or anything else that a behavior-preserving refactor would legitimately change. **Tests that bind to implementation are worse than no test** — they pass while the system is broken, fail while the system is correct, and convert every refactor into a test rewrite that silently re-encodes the same assumption. The litmus test: *"Could a teammate rewrite this unit's internals from scratch — different functions, different data structures, different control flow — and keep my tests passing as long as the externally-observable behavior is unchanged?"* If no, the test is testing implementation and must be rewritten before merge. Mock-heavy tests, snapshot tests of internal structures, and assertions that re-spell the source code are the common shapes of this violation. Asserting on exact byte sequences is legitimate only where the bytes ARE the contract (e.g. `ESC[200~…ESC[201~` paste framing, `\r` submit — §9.3), not as a transcript of internal calls.
- **An injection seam exposes a domain concept, NOT the shape of the thing behind it.** This is the observable-behavior rule applied to the *production interface*: a dependency injected for testability — the filesystem, a clock, the source of some stream of events — is part of the unit's public surface, so it MUST name *what* the unit needs in the unit's own vocabulary (`canEnter(dir): boolean`, `now(): number`, `summaries(): Span[]`), never the primitives that happen to satisfy it today (`accessSync`/`statSync`, `Date.now`, a concrete tracker's fields). A seam that enumerates library or syscall shapes leaks the implementation through the back door: the test assertion can look behavioral while the fake the test constructs re-spells the mechanism, so a behavior-preserving change to *how* the dependency is met breaks the interface and every fake at once. Same litmus as the assertion rule, aimed one layer out: *could a teammate swap the mechanism — different syscalls, a different library, a folded-together check — and leave the seam and its fakes untouched?* If no, narrow the seam to the concept. Inject the **narrowest domain predicate** that makes the otherwise-unreachable branch testable (an enterability check, not three `fs` calls), and let the real implementation of that predicate be covered by real fixtures wherever the environment permits; gate the genuinely-unprovokable case (e.g. a traverse-permission failure that cannot occur as root) with `it.skipIf` rather than widening the seam. The existing shapes to copy: `bootstrapCommands.ts` injects the CommandTracker's public slice, and `UI-STANDARDS.md` organisms take services injected (never reached for) — both name the concept, not the backing.
- **Comments state ONLY what the code cannot — if a fact is recoverable by reading the code, commenting it is forbidden.** The test is mechanical and absolute: *could a reader delete this comment, read only the code, and recover the same fact?* If yes, **delete the comment.** That covers narration (restating a line, a signature, a type, a data structure, a control-flow step, a variable name) **and** any description of the *current mechanism* — mechanism descriptions drift the instant the mechanism changes, and a behavior-preserving refactor must never be able to falsify a surviving comment (the stale "single carried slot" sitting beside a per-repo map is the canonical failure this rule exists to kill). A comment earns its place by carrying a fact that originates **outside the code it annotates** and that the code therefore cannot hold. Exactly two kinds qualify:
  - **An external contract or authority.** A spec clause (`§n`), a web standard criterion (WCAG / WAI-ARIA), a wire or terminal protocol (OSC 7/133, bracketed-paste framing), an external file-format or API schema (the agent-loop `state.yaml` vocabulary), or a fixed product/workflow constraint ("injects nothing; the human drives agent-loop by hand"). **Cite it — never re-explain it in prose.** The citation is the whole comment; a paragraph restating what the spec says is narration of an external doc and is forbidden.
  - **A cross-module coupling this codebase cannot express through an abstraction.** An implicit dependency between two deep modules where a future edit on one side would silently break the other **and no type, name, test, or assertion can catch it.** This is the *only* license to mention anything internal — and it is conditional: first try to make the coupling unbreakable in code (a shared type, a precise name, a pinning test). Comment only the residue no abstraction can hold, and state **what breaks if the coupling is violated**, never how the code currently works. "Outside the system" extends this far and no further: across a deep module boundary inside this repo, only when omission risks a break no abstraction would catch.

  Everything else goes. Prefer a precise name, a named test, or a `§n` citation over any sentence. Doc-comments on exported identifiers are allowed but must add the caller-facing contract (obligations, external invariants) — not echo the signature or types. `// TODO(owner): …` tags and recorded §12-style gaps are always allowed. When in doubt, delete: a missing comment costs a code read; a wrong one costs a misled change.
- **No mocks for the terminal emulator or the PTY.** Integration tests drive the real `@xterm/headless` shadow module with scripted byte streams (it is pure JS and runs under vitest/node). Full-loop behavior (real node-pty, real bash, real renderer) is covered by Playwright `_electron` e2e — never by mocking node-pty. Fake timers/clocks are fine (the quiescence detector takes injectable timers for exactly this); mocking the VT parser is not.

## Tracer-bullet development (mandatory planning requirement)

**Every implementation plan for §24.2 backlog work MUST be decomposed into tracer-bullet slices before any code is written. This is a planning gate: a plan that is not sliced this way is incomplete and implementation does not start.**

A **tracer bullet** is a thin but *complete* vertical slice that passes through **every layer the feature touches** — main-process logic → the typed IPC contract (`src/shared/ipc.ts`, §6) → preload bridge → renderer widget → visible, interactive UI — and does the **smallest real end-to-end thing** with **real backing, not a fixture**. Like a tracer round, you fire it through the running app and watch where it lands: each slice is hand-testable through the UI (`pnpm run dev`) and demoable on its own.

Each slice MUST satisfy all of:

1. **Back-to-front, never layer-by-layer.** A slice spans main, `ipc.ts`, preload, and renderer as far as that increment needs, so it is exercisable from the UI. Building a whole horizontal layer — the complete main-process subsystem, the entire IPC surface, or a data store — as its own phase with nothing in the UI to fire it is **forbidden**. If a slice cannot be fired from the UI, it is cut too wide or wrong; narrow it until it can.
2. **Replaces one mock with real backing, incrementally.** §24.1 stands the widgets up fixture-driven (§24); a slice swaps **one** fixture path for its real subsystem and leaves the app still running and the visible product never regressed.
3. **Ends testable through the UI, RED-first.** Each slice carries the full **Test-driven development** ladder above (failing test first, observed), and that ladder MUST include a **Playwright `_electron` e2e that drives the real loop** (real PTY, main, renderer) — because the slice's contract *is* "a user does X in the app and sees Y." Main-process integration tests and renderer DOM unit tests sit underneath it.
4. **Named in the plan.** For every slice the plan states three things: the **user-visible action** that fires the bullet, the **observable result in the UI**, and the **e2e that proves it**. A slice missing any of the three is not yet planned.

This is the §24 "UI-inwards" build direction applied feature by feature: stand the skin up, then drive real subsystems through it one fireable slice at a time. Horizontal "finish the backend, then wire the UI later" plans are a planning-level defect — reject and re-slice.

## Code standards

- TypeScript, `strict: true`. No `any` in `src/shared/ipc.ts` — the IPC contract is the part TS exists to protect.
- `@xterm/xterm` and `@xterm/headless` are **pinned to the same exact version** (§8.2): two parsers at different versions silently corrupt captures. Bump them only together.
- Security defaults are non-negotiable: `contextIsolation: true`, `nodeIntegration: false`, paste-breakout sanitization (`ESC[201~` strip) on **both** injection paths (§7.5, §9.3).
- **Untrusted data crossing a boundary travels as data, never as syntax.** Anything that crosses a process, shell, or OS boundary into a place where the far side interprets it is carried as a structured value — an env var, an `argv` element, a quoted literal — and is **never concatenated into a string the far side parses**. The existing instances are this rule applied at specific boundaries: paste-breakout sanitization at the injection seam (§7.5/§9.3) and the §23.5 launch target crossing the OS boundary as a distinct env value rather than spliced into a command line (CWE-78). When the boundary is a POSIX shell specifically, the enforcement is the bullet below.
- **Any value placed into shell text is quoted through `src/shared/shellQuote.ts` — never hand-rolled.** Generated scripts, PATH/profile blocks, command lines, and pasted paths all route through the one shared primitive (the shared-semantics rule above; CWE-78). `shellQuote` is lossless — it only quotes; lossy paste-safety (e.g. C0-control stripping before a drop reaches the prompt, §7.8) is a separate layer the caller applies *before* quoting, never folded into the primitive.
- **No code in the production system modifies the user's `.gitignore` — ever.** Whether to ignore or commit a path is the user's VCS decision, not the app's. App-owned files (`flow-state.yaml`, the audit pointer, `todos.json`, anything under `.agent-terminal/`) are written wherever the spec puts them, but the code that writes them **never** creates, appends to, or otherwise edits `.gitignore` to "protect" them — a per-file ignore entry is redundant in a repo that already ignores the directory and is unwanted churn besides (§19.1/§25; the todoStore §16.3 is the reference — it never touched `.gitignore`). RED-first tests for any app-owned persistence MUST assert the write **creates no `.gitignore`** and leaves a pre-existing one **byte-for-byte unchanged**. (This generalizes: the production system does not silently rewrite a user's tooling config — `.git/`, editor configs, shell rc files outside the explicit, user-invoked §23.5 install action — to make its own state tidy.)
- Bracketed-paste mode is read live at injection time (renderer: `term.paste()`; main: `shadow.modes.bracketedPasteMode`) — never cached, never decided by us (§9.3).
- **Renderer UI follows `UI-STANDARDS.md`.** Build atomic (Atoms · Molecules · Organisms), test each component individually (DOM-level unit tests for atoms/molecules; organisms also get e2e + a relocation test proving they move between frames unchanged). Organisms are factories with a typed interface (`createX(host, deps)`), touch only their host subtree, take services injected (never reached for), signal across components through the contract (not DOM reach-across), and theme via `tokens.css` only. This is the §22.4 layout-as-data boundary generalized.
- The monitor pane talks only to `window.monitor.*` (§9.1). It must never import from terminal/selection modules or touch renderer xterm state, even though they share a document — this is what keeps it relocatable to a separate process. It is the canonical example of the `UI-STANDARDS.md` stable-interface rule.
- Timing values are named and configurable where the spec says so: `SUBMIT_DELAY_MS` via `APP_SUBMIT_DELAY_MS`, `QUIET_MS`, the 80 ms resize/settle debounces (§7.1, §8.2, §9.3). No new magic-number sleeps.
- Every IPC payload carries `sessionId` (§6), even while there is only one session.
- **A best-effort or cosmetic side effect must never be able to abort the critical path it sits on.** Anything observe-only or decorative — setting the Dock icon, writing the §25 audit record, any fire-and-forget telemetry — is wrapped so a failure inside it cannot propagate into its caller. The §25 audit recorder already states this ("never throws into the flow path"); the rule is general, because the inverse is exactly how a cosmetic failure (a `setIcon` throw that aborted `createWindow` before the window existed) once turned the *entire* e2e bar red with no product cause. The litmus: if this effect threw, would a feature the user actually depends on stop working? If yes, the effect is on the critical path by accident — isolate it (try/catch that leaves a sensible default, or a non-throwing boundary) so its failure is contained and, where it matters, recorded. This is the robustness dual of the TDD evidence rule: don't let an inessential effect manufacture a red bar that masks — or mimics — a real one.

## Ticket standards (agent-loop ready)

Tickets are GitHub issues. A ticket is **agent-loop-ready** only when a human applies the **`agent-loop/ready`** label — the single "pickable now" signal (`agent-loop available` lists them; `agent-loop pickup <n>` assigns it, strips the label, and opens a draft PR that `closes #<n>`). Do not add `agent-loop/ready` yourself; it means *a human has vetted the ticket against everything below*.

The issue **body is the intent contract** — agent-loop bundles the title, body, and comments verbatim into `.agent-loop/pr-context.md`, which the work agent and all nine persona reviewers read. Vague body → vague plan and reviews.

### Required content

Every ready ticket MUST contain:

1. **Title** — a crisp imperative (`Persist flow inputs across steps`), not a topic.
2. **Problem / context** — what's wrong or missing and why it matters. Cite the spec: `terminal-web-ui-spec.md §n` (the spec wins; if the ticket diverges, say so and add a changelog entry).
3. **Scope** — the concrete change to make, described as outcomes.
4. **Non-goals** — what this ticket explicitly does *not* do, so reviewers don't grade against absent work.
5. **Acceptance criteria** — see the AC rule below. This is what `review-intent` grades "done" against; without it the loop cannot catch an incomplete feature.
6. **Affected contracts** — if the change alters an external contract, say so and describe the observable contract *behavior*, pointing to `src/shared/ipc.ts` as where the typed contract lives. State "no contract change" when none. (Do not prescribe channel/payload names — that's an implementation decision.)
7. **Standards that apply** — by reference only: link the governing docs (TDD/RED-first, `UI-STANDARDS.md`, the tracer-bullet rule, relevant `§n`) so reviewers can cite them.

### Writing rules

These are non-negotiable for every ticket:

- **Acceptance criteria are measurable outcomes ONLY** — observable behaviors phrased so each becomes a test (user does X → observes Y). The sole exception is a ticket **inherently technical in nature** (support for a technical standard, an API implementation, a specific algorithm, and the like), which may state technical criteria directly.
- **Nothing that can drift.** A ticket MUST NOT contain anything that could change under normal activity — merging another branch, implementing the ticket itself, or making a reasonable implementation decision. No line numbers, current counts, "the function below," or any other detail that goes stale the moment work begins.
- **No implementation.** A ticket MUST NOT contain statements in the realm of *how* to build it. Point to the relevant repository standards **by reference only**; never inline the approach.
- **Unambiguous.** Avoid statements open to more than one reading. Write one clear meaning per statement; add clarifying language only where genuinely necessary.
- **No internal conflict.** A ticket MUST NOT contradict itself or any existing standard — **unless** the conflict is an explicit user instruction, in which case the ticket MUST state clearly that it is an explicit user instruction (and why it overrides the standard).

### Tracer-bullet tickets (§24.2 backlog)

A §24.2 ticket MUST name the three things the tracer-bullet rule requires: the **user-visible action** that fires the slice, the **observable result in the UI**, and the **e2e that proves it**. A ticket missing any of the three is not ready.

### Ready checklist

All must hold before the `agent-loop/ready` label goes on:

- [ ] Title is an imperative; body states problem, scope, **non-goals**.
- [ ] Acceptance criteria are measurable outcomes (or justified technical criteria).
- [ ] No drift-prone detail; no implementation (standards by reference only).
- [ ] Every statement is unambiguous; no internal or standards conflict (explicit user overrides labeled as such).
- [ ] Affected contracts described by behavior (or "none"); §24.2 work names action + result + e2e.
