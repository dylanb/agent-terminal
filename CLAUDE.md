# CLAUDE.md

Agent Terminal — Electron app that hosts coding agents (Claude Code, Codex, …) in a PTY-attached shell session, renders it with xterm.js, tees output into a main-process `@xterm/headless` shadow screen model, and provides a monitor pane that captures output and injects input back into the agent.

`terminal-web-ui-spec.md` is the authoritative spec. Every subsystem implements a numbered section of it; when code and spec disagree, the spec wins — or the spec gets a changelog entry. Cite spec sections (e.g. §9.3) in code review discussion rather than re-arguing settled design decisions.

## Commands

This repo uses **pnpm** (see `packageManager` in `package.json`). `.npmrc` pins `node-linker=hoisted` so `@electron/rebuild` and electron-builder see a flat `node_modules`; `pnpm.onlyBuiltDependencies` allows node-pty/electron/esbuild to run their install scripts (pnpm v10 blocks build scripts by default).

```
pnpm install        # runs the postinstall electron-rebuild for node-pty automatically
pnpm run rebuild    # electron-rebuild -f -w node-pty — REQUIRED after install or Electron bump
pnpm run dev        # electron-vite dev (renderer HMR)
pnpm run build      # type-check + electron-vite build
pnpm test           # vitest, both projects: `node` (tests/unit + tests/integration) and `browser` (tests/browser).
                    # The `pretest` hook provisions the Chromium the `browser` project needs (a cached no-op after the first run).
./scripts/e2e-podman.sh        # playwright _electron e2e in Podman/Xvfb — the canonical local e2e run (real PTY/display)
./scripts/e2e-podman.sh "<-g>" # filter to matching tests
pnpm run test:e2e   # raw playwright e2e — needs a focusable display; on macOS a bare subprocess launch can't focus, so prefer the Podman harness above
```

**Always run the e2e locally via the Podman harness (`docs/e2e-podman.md`) before claiming a change done — do not defer e2e to CI.**

`node-pty` is a native module compiled against Electron's ABI. If main-process startup fails with a NODE_MODULE_VERSION error, run `pnpm run rebuild`.

## Requesting / awaiting a Copilot PR review

Use `scripts/await-copilot-review.sh <pr> [--request] [--check]` (portable bash; macOS + Linux, no `jq`) — **never hand-roll a poll.** The script's header documents the two non-obvious traps it removes (the Copilot login differs by API surface; a wrong poll predicate is indistinguishable from "not posted yet"). If you must filter reviews yourself, match `user.type=="Bot"` + a case-insensitive `copilot`, not an exact login.

## Architecture (orientation only — details in the spec)

- `src/main/` — PTY lifecycle (§5), shadow terminal + quiescence (§8), injection API (§9.3), IPC handlers. node-pty and the shadow live here, never in the renderer. The flow **audit recorder** (§25) also lives here (`auditRecorder.ts` + `auditPaths.ts`): observe-only, best-effort, it writes each run's append-only YAML under `~/.agent-terminal/audit/` and never throws into the flow path.
- `src/preload/` — contextBridge exposing the `term` and `monitor` namespaces (§6). No raw `ipcRenderer` in the renderer.
- `src/renderer/` — terminal pane (xterm + app-owned selection, §7) and monitor pane (§9).
- `src/shared/ipc.ts` — the typed IPC contract. This file is the single source of truth for channel names and payload shapes; main, preload, and renderer all import from it.
- **Semantics shared by main and renderer get one definition in `src/shared/`, imported by both — never re-implemented per side.** This generalizes the `ipc.ts` rule from the wire shape to the *meaning* on top of it: any classification or identity that both processes must agree on — what counts as "the same occurrence" for dedup, which statuses mean "blocked on a human", and the like — lives in a shared module so the two sides cannot drift. Two parallel copies that "obviously agree today" are the bug; a behavior-preserving change to one side must be unable to desync them. The current examples are `src/shared/occurrence.ts` (dedup identity), `src/shared/loopStatus.ts` (human-needed classification), `src/shared/audit.ts` (the §25 audit vocabulary, event classifiers, serialize↔parse pair, and timeline reconstructor — one definition for the main-process writer, the tests, and a future viewer), and `src/shared/shellQuote.ts` (POSIX shell quoting — one primitive for the main-process shim/PATH generation and the renderer's drop-to-paste path).
  - **The boundary is any two sides that must agree on the same serialized vocabulary — not just main↔renderer.** A writer and a reader of the same on-disk file are two sides of one contract exactly as two processes are, and they desync the same way. `loopStateWriter` persisted `error_reason` whenever a reason was supplied while `agentLoopBridge` decoded it only under `status: error`: two hand-maintained copies of one gate, in agreement right up until they weren't. When one module serializes a vocabulary and another parses it, the predicate that decides what is legal lives in **one** module both import.
- **Code that writes an asset another component later reads computes the destination through that component's own resolver — never a parallel path literal.** This is the writer↔reader axis of the shared-semantics rule above: both sides derive the location from one exported resolver, so the write target and the read source cannot drift. Pin it with an `expect(dest).toBe(resolve…(…))` test. It binds a build step placing an asset for runtime code (`appIconBuild.ts` and `exampleAssetsBuild.ts` write to the destinations `resolveWindowIconPath` / `resolveExampleFlowDir` return — the same functions `index.ts` reads at runtime) and equally an installer seeding a directory some other module, or another process entirely, discovers from.
  - **Corollary — when the reader's resolution is precedence-aware, the writer targets a named branch of that order, not the resolver's result.** A resolver that consults an override chain (repo-local override, else the user-config copy) answers "where would this be read *from here, right now*"; a writer that calls it inherits ambient state it does not control, so the same install lands somewhere different depending on the cwd. Name the branch the writer means — "the user-config loops directory" — give it its own definition, and let the precedence-aware resolver consume that same definition for its fallback leg. The pin must be against the branch, and the test that holds it installs **with an override present**: a no-override fixture passes either way, so it proves nothing.
  - **Corollary — a writer that seeds a directory absent on first run has a RED test that deletes the target's root first.** Same failure shape as the override-present pin above, on the other axis: a fixture built with `mkdtemp` pre-creates the destination's whole parent chain, so a confinement or resolver that only works when the anchor already exists passes every such test while failing on the fresh machine the feature is *for*. The install nearly shipped a jail anchored with `resolveJail(dirname, basename)` — which returns `null` when the parent (`~/.claude`) is absent — and every test was green because the fixtures always created the config root. The test that holds a first-run writer must remove the user-config root (`~/.claude`, the `.agent-terminal` global dir, …) before asserting the tree is created: a pre-created-root fixture proves nothing about first run, exactly as a no-override fixture proves nothing about the override branch.

## Test-driven development

- **TDD is mandatory for every code change — RED first, no exceptions.** No code gets written without a failing test being written and run first. Write the failing test, run it and observe the failure (the assertion message, not just an exit code), then make it pass with the smallest change that does so, then refactor. This applies to bug fixes (start with a regression test that reproduces the bug), new features (start with a test for the acceptance criterion), refactors of behavior-bearing code (start with a pinning test against the current behavior), and API changes (start by updating the test to the new contract and watching it fail to compile or fail at runtime). Tightening an existing test until it would catch the bug counts as a new test.
  - **Glue and wiring are code.** Button handlers, event subscriptions, IPC wiring, lifecycle hooks — all of it. A passing test for a lower-level helper does **not** license writing the layer above it untested: the failing test must observe the *change's own* behavior at its own observable boundary. If the change wires a button, the RED test clicks the button (e2e or DOM-level); if it subscribes to an event, the RED test fires the event and observes the consequence. "A test exists nearby" is the loophole that produced this rule.
  - **The sole exemption is code that cannot be covered at all.** Claiming it requires, *before any code is written*: (1) an explicit written statement of exactly what cannot be tested and why no layer of the stack (unit, integration, Playwright e2e) can observe it, and (2) a recorded gap — an unchecked §12-style checklist item or `// TODO(owner):` — so the hole is visible, never discovered later. "Untestable" is a design smell, not a license, and "hard/slow to test" (process-table checks, alt-buffer gestures, timing) does not qualify — those get the slow test.
  - Edits with nothing observable to test — comment/doc-only changes, formatting — are outside the rule's scope, but anything that can alter behavior (including renames, config, build files, dependency bumps) is in: if existing tests can't fail when the edit is wrong, write one that can, or invoke the exemption above in writing.
  - Tests written after the implementation are pinning tests, not TDD — they never satisfy this rule for new code. Calling tests "manual verification" or "I'll add tests after" is never acceptable.
- **Evidence of a clean, complete test run is required before declaring any change clean, done, or ready for review — no exceptions.** "Clean/done/ready" is a claim about observed reality, not about the diff: you MUST have run the *full* relevant suite (unit, integration, and the Playwright e2e — the e2e green bar needs a focusable display, so **always run it locally in the Podman/Xvfb harness** (`./scripts/e2e-podman.sh`, `docs/e2e-podman.md`) and **never defer e2e evidence to CI**; a macOS subprocess launch cannot give focus/clipboard and its red bar is not evidence of anything) and seen it pass. Show the evidence — the passing tally — when you make the claim. A suite that has never been observed green in a valid environment is **worse than no suite**: its redness gets pre-explained as "the environment" and stops being a signal, which is exactly how a real defect (e.g. a synchronous throw that aborted window creation and turned the entire e2e bar red) hides in plain sight. **A failing or unrunnable test — or broken test infrastructure — is never a thing to normalize, defer, or explain away.** The e2e is runnable locally via the Podman harness, so "I'll let CI run it" is not an acceptable substitute for running it yourself; **only** when the Podman harness itself cannot run (Podman absent, machine unprovisionable) is it grounds to declare an impasse and ask the operator for help. Either get to a clean complete run locally, or stop and escalate; never report "clean" over a red or un-run bar, and never push and rely on CI in place of a local Podman e2e run.
- **Tests MUST exercise observable behavior, NOT implementation.** **Treating this as optional is a blocker-level violation.** A test asserts what a caller of the unit-under-test can observe from the outside: return values, thrown errors, bytes written to the PTY, IPC payloads emitted on a contract channel (§6), text read back out of the shadow buffer through its public read path, DOM state the user can see. A test MUST NOT assert: which private method was called, in what order, how many times; the internal data structure shape; the exact escape-sequence parsing steps; the names of intermediate variables; or anything else that a behavior-preserving refactor would legitimately change. **Tests that bind to implementation are worse than no test** — they pass while the system is broken, fail while the system is correct, and convert every refactor into a test rewrite that silently re-encodes the same assumption. The litmus test: *"Could a teammate rewrite this unit's internals from scratch — different functions, different data structures, different control flow — and keep my tests passing as long as the externally-observable behavior is unchanged?"* If no, the test is testing implementation and must be rewritten before merge. Mock-heavy tests, snapshot tests of internal structures, and assertions that re-spell the source code are the common shapes of this violation. Asserting on exact byte sequences is legitimate only where the bytes ARE the contract (e.g. `ESC[200~…ESC[201~` paste framing, `\r` submit — §9.3), not as a transcript of internal calls.
- **An injection seam exposes a domain concept, NOT the shape of the thing behind it.** This is the observable-behavior rule applied to the *production interface*: a dependency injected for testability — the filesystem, a clock, the source of some stream of events — is part of the unit's public surface, so it MUST name *what* the unit needs in the unit's own vocabulary (`canEnter(dir): boolean`, `now(): number`, `summaries(): Span[]`), never the primitives that happen to satisfy it today (`accessSync`/`statSync`, `Date.now`, a concrete tracker's fields). A seam that enumerates library or syscall shapes leaks the implementation through the back door: the test assertion can look behavioral while the fake the test constructs re-spells the mechanism, so a behavior-preserving change to *how* the dependency is met breaks the interface and every fake at once. Same litmus as the assertion rule, aimed one layer out: *could a teammate swap the mechanism — different syscalls, a different library, a folded-together check — and leave the seam and its fakes untouched?* If no, narrow the seam to the concept. Inject the **narrowest domain predicate** that makes the otherwise-unreachable branch testable (an enterability check, not three `fs` calls), and let the real implementation of that predicate be covered by real fixtures wherever the environment permits; gate the genuinely-unprovokable case (e.g. a traverse-permission failure that cannot occur as root) with `it.skipIf` rather than widening the seam. The existing shapes to copy: `bootstrapCommands.ts` injects the CommandTracker's public slice, and `UI-STANDARDS.md` organisms take services injected (never reached for) — both name the concept, not the backing. Corollary for a descriptor with mutually-exclusive modes: model it as a discriminated union, never a flat record whose fields are dead in some modes — a flat shape lets a caller construct or pass a field the mode ignores (a dummy value), which re-leaks the branch structure the seam should hide. `BundleLocation` (`packaged: true` carries `resourcesPath`; `packaged: false` carries `appPath`) is the shape to copy.
- **Comments state ONLY what the code cannot.** Mechanical litmus: could a reader delete the comment, read only the code, and recover the fact? If yes, delete it — that bars all narration *and* every description of the current mechanism (which rots the instant the mechanism changes). Exactly two comments earn their place: an **external contract/authority** cited (`§n`, WCAG/WAI-ARIA, a wire or file-format protocol) with no prose gloss beside the citation, and a **cross-module coupling no type, name, or test can catch**, stating what breaks if it is violated. Corollaries: an asserted invariant is a missing check — enforce it and delete the comment; a parameter's domain goes in a named type, not doc-comment prose; a mechanism comment the change alters is updated or deleted in that same change. `// TODO(owner):` tags and §12 gaps are always allowed. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- **No mocks for the terminal emulator or the PTY.** Integration tests drive the real `@xterm/headless` shadow module with scripted byte streams (it is pure JS and runs under vitest/node). Full-loop behavior (real node-pty, real bash, real renderer) is covered by Playwright `_electron` e2e — never by mocking node-pty. Fake timers/clocks are fine (the quiescence detector takes injectable timers for exactly this); mocking the VT parser is not.
- **No mock CSS engine either — a test that grades a painted pixel asks a browser what it painted.** Assertions about colour, contrast, or the focus ring go in the `browser` vitest project (`tests/browser/`, real Chromium) or the Playwright e2e, and read `getComputedStyle`; the test does the WCAG arithmetic and nothing else. Never re-derive a painted value by parsing `styles.css` — resolving `var()`, `color-mix()`, specificity and document order is the engine's job, and a regex that approximates it is the same class of error as mocking the VT parser. The rule is not stylistic: the parser this replaced modelled the cascade as "the later-named rule always wins" and matched one exact selector string, so a group `opacity` on a higher-specificity selector, an `opacity` on an ancestor, and an equal-specificity rule reclaiming `color` all left the suite green over a control that had lost its focus ring (WCAG SC 1.4.11). A pin that cannot fail when the pixel is wrong is worse than none.
- **An e2e test never boots an Electron it will not use — a test that launches its own is tagged `@ownapp` and the harness boots nothing for it.** An Electron boot (real PTY, real bash, real renderer) is the most contended thing the suite does, so a `beforeEach` that boots one for a test which immediately closes it and relaunches with a bespoke env spends a full startup — and the wait on its first paint — to be discarded. This is a correctness rule: the cost lands on process startup, and a saturated runner fails as a missed startup budget, a test past the 60 s ceiling, and a **worker that cannot tear down** — and a worker-teardown timeout belongs to no test, so `retries` cannot absorb it and the run exits non-zero with every test green (`1 error was not a part of any test`). The canary at the top of `app.spec.ts` pins the contract so a regressing `beforeEach` fails a test instead of quietly taxing every run. Generally: when a shared fixture is expensive and only *some* tests can use it, provisioning it for everyone is not the safe default. → [CODE-STANDARDS.md](CODE-STANDARDS.md)

## Tracer-bullet development (mandatory planning requirement)

**Every implementation plan for §24.2 backlog work MUST be decomposed into tracer-bullet slices before any code is written. This is a planning gate: a plan that is not sliced this way is incomplete and implementation does not start.** A tracer-bullet slice is a thin but *complete* vertical slice — main → `ipc.ts` → preload → renderer → visible UI — that does the smallest real end-to-end thing with real backing, fireable from the UI and RED-first with an `_electron` e2e. The definition and the four criteria each slice must satisfy live in **[TRACER-BULLET.md](TRACER-BULLET.md)** — a plan is graded against that file.

## Code standards

The imperatives below are the enforceable rules. **[CODE-STANDARDS.md](CODE-STANDARDS.md)** carries each
linked rule's rationale, motivating defect, and named primitive — cite that file's section in review
rather than re-arguing a settled decision.

- TypeScript, `strict: true`. No `any` in `src/shared/ipc.ts` — the IPC contract is the part TS exists to protect.
- `@xterm/xterm` and `@xterm/headless` are pinned to the same exact version (§8.2) — two parsers at different versions silently corrupt captures. Bump only together.
- Security defaults are non-negotiable: `contextIsolation: true`, `nodeIntegration: false`, paste-breakout `ESC[201~` strip on both injection paths (§7.5, §9.3).
- Untrusted data crossing a process/shell/OS boundary travels as a structured value (env var, `argv` element, quoted literal), never concatenated into a string the far side parses (CWE-78). → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Any value placed into shell text is quoted through `src/shared/shellQuote.ts`, never hand-rolled (CWE-78). → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Any path derived from repo content is confined through `src/main/confinedPath.ts` before it is walked, opened, or written, never hand-rolled (CWE-22/59/367). Which jail you name depends on whose ground it sits on — `resolveJail` for a jail inside untrusted content, `resolveOwnedDirJail` for a root in the user's own space — and getting that backwards is the bug. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- A caught value's two questions — "which errno is it?" and "what do I tell the user?" — are answered by `src/main/errno.ts` (`isErrno` against a closed `ErrnoCode` union, `errMsg`), never inline. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- A tree-walk whose emptiness would be a silent DATA problem uses `src/main/dirEntries.ts` — absent yields `[]`, unreadable throws. Conflating them reports a successful install of nothing. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- No production code modifies the user's `.gitignore`, ever (§19.1/§25); RED-first persistence tests assert the write creates no `.gitignore` and leaves a pre-existing one byte-for-byte unchanged. The only exemption is an explicit, user-invoked install action — an exemption from *silence*, not from care. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Bracketed-paste mode is read live at injection time (renderer `term.paste()`; main `shadow.modes.bracketedPasteMode`) — never cached, never decided by us (§9.3).
- Renderer UI follows **[`UI-STANDARDS.md`](UI-STANDARDS.md)** — atomic tiers, per-component tests (organisms also get e2e + a relocation test), typed `createX(host, deps)` factories, host-subtree only, services injected, `tokens.css` theming. The §22.4 layout-as-data boundary generalized.
- The monitor pane talks only to `window.monitor.*` (§9.1) — never imports terminal/selection modules or touches renderer xterm state, which is what keeps it relocatable to a separate process.
- Timing values are named and configurable where the spec says so: `SUBMIT_DELAY_MS` via `APP_SUBMIT_DELAY_MS`, `QUIET_MS`, the 80 ms resize/settle debounces (§7.1, §8.2, §9.3). No new magic-number sleeps.
- Every IPC payload carries `sessionId` (§6), even while there is only one session.
- Every IPC payload carries the identity of the resource it acts on; the receiver never re-derives that target from ambient state — a data-loss defect for destructive or outward-facing actions. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- A best-effort or cosmetic side effect must never abort the critical path it sits on; wrap it, and coerce every caught value as `unknown` (`e instanceof Error ? e.message : String(e)`). → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Never silently swallow an error whose consequence is a state the user cannot recover from through the UI — surface it and leave a retry/back-out path. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Never allow an unrecoverable state to occur: every operation rolls back to the prior good state or forward to one with a visible next action. When unsure whether a path has a UI route out, ask the operator before building it. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- The policy authorizing a destructive operation is checked at the operation (not at the prompt that precedes it) and hard-fails before any prompt is raised. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- One theme per PR — a branch that grows a second theme wants a second PR, or a per-theme review checkpoint when they must land together. A friction/churn fix encountered *while doing the theme's work* is **not** a second theme. → [CODE-STANDARDS.md](CODE-STANDARDS.md)
- Fixing churn or dev friction you hit while doing a PR's work is REQUIRED in that same PR — not deferred, not optional. The boundary is the source of the discovery, not the file it touches. → [CODE-STANDARDS.md](CODE-STANDARDS.md)

## Ticket standards (agent-loop ready)

Tickets are GitHub issues. A ticket is **agent-loop-ready** only when a human applies the **`agent-loop/ready`** label — the single "pickable now" signal (`agent-loop available` lists them; `agent-loop pickup <n>` assigns it, strips the label, and opens a draft PR that `closes #<n>`). **Do not add `agent-loop/ready` yourself** — it means *a human has vetted the ticket against the full authoring contract*. The issue **body is the intent contract**: agent-loop bundles the title, body, and comments verbatim into `.agent-loop/pr-context.md`, which the work agent and all nine persona reviewers read, so a vague body yields a vague plan and reviews.

The full authoring contract a ticket must satisfy before that label goes on — required content, writing rules, tracer-bullet-ticket requirements, and the ready checklist — lives in **[TICKET-STANDARDS.md](TICKET-STANDARDS.md)**. Author and groom tickets against that file.
